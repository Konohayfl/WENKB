## 1. 文档目的

本文档用于记录后续围绕 WenKB 项目提出的架构问题、技术概念问题和实现理解问题。

每当用户提出相关疑问时，应先结合项目需求分析、概要设计、详细设计、数据库设计、接口设计和当前代码进行解答，再将问题与解答追加到本文档，形成可持续复习和交接的知识记录。

## 2. 适用范围

本文档记录以下类型的问题：

- 系统总体架构、分层职责和模块边界。
- 知识库、数据集、文档、索引、向量检索和问答流程。
- 数据库表结构、状态流转、数据一致性和持久化策略。
- LLM、embedding、RAG、摘要、Q&A、三元组等技术概念。
- 前后端交互、接口设计、异步任务、配置管理和部署运维。
- 阅读项目代码时产生的具体实现疑问。

## 3. 解答约定

回答问题时应遵循以下原则：

1. 先给出简明结论，再解释原因和关键概念。
2. 明确区分“项目设计目标”“当前代码实现”和“可改进方案”。
3. 涉及项目行为时，优先引用对应的设计文档、接口约定或代码位置。
4. 涉及多个概念时，说明它们之间的关系，并尽量结合 WenKB 的实际流程举例。
5. 发现设计与实现不一致时，记录差异、影响和建议，不直接把实现现状描述为设计基线。
6. 对不确定或需要进一步验证的内容，明确标记验证结论和验证方式。

## Q1：向量索引和 embedding 模型如何协作

提问日期：2026-09-04\r\n分类：概念、架构、实现\r\n关联文档：[概要设计](architecture_design.md)、[详细设计](detailed_design.md)、[数据库设计](database_design.md)、[开发环境与使用手册](development_environment_setup.md)；代码：[向量库适配](../wenkb-server/server/core/tools/repos_vector_db.py)、[索引构建](../wenkb-server/server/core/tools/dataset_to_vector.py)、[模型适配](../wenkb-server/server/core/tools/llm_client_tools.py)、[问答检索](../wenkb-server/server/core/tools/ask_to_llm.py)

#### 问题

解释一下向量索引、embedding 模型，并说明它们在 WenKB 中如何协作。

#### 简明结论

embedding 模型负责把文本转换成能够表达语义的数值向量；向量索引负责保存这些向量并快速找出与查询向量最相近的内容。WenKB 对每个知识库使用一个持久化的 Chroma 集合，文档分段、摘要、Q&A 和三元组都可以经过同一个知识库绑定的 embedding 模型后写入集合，再通过相似度检索为问答和搜索提供上下文。

#### 详细解答

### 1. embedding 模型是什么

embedding（嵌入）模型是一类把文本映射为固定长度向量的模型。例如，文本“如何重建知识库索引？”经过模型后会得到一组浮点数：

```text
[0.12, -0.03, ..., 0.47]
```

向量中的单个数字通常没有可直接解释的业务含义，但整体位置可以表示文本的语义特征。语义相近的文本，通常会在向量空间中更接近，因此“如何重建索引”和“知识库索引如何重新构建”即使字面不同，也有机会被检索为相近内容。

embedding 模型与 LLM 的职责不同：

- embedding 模型主要用于“表示和比较”，输出向量，不负责直接生成完整答案。
- LLM 主要用于“理解上下文和生成”，根据检索到的片段组织答案。
- embedding 模型的向量维度、分词方式和训练语义空间属于模型自身特征；更换模型后，旧向量不能直接当作新模型的向量使用。

### 2. 向量索引是什么

向量索引是面向向量相似度查询的数据结构和存储能力。它通常保存以下信息：

- 唯一 ID：定位原始分段或增强对象。
- 文本或文档：检索命中后提供给上层使用。
- embedding 向量：用于距离或相似度计算。
- metadata：保存数据集、文件、分段和来源对象等溯源信息。

它与关系数据库中的普通字段索引不同：普通索引适合精确匹配、范围查询或排序，向量索引适合回答“哪些内容在语义上最接近这个问题”。向量库也不等于原始业务数据库：WenKB 的关系库保存业务事实和状态，向量库保存检索所需的文档及向量副本，两者需要通过稳定 ID 和 metadata 关联。

### 3. WenKB 的索引构建流程

1. 创建知识库时绑定 embedding 模型，知识库记录中的 `vecModlId` 决定后续使用的模型。
2. 数据集进入索引任务后，系统读取文件、网页或文档版本内容，并按文件类型切分文本。当前实现的普通分段参数为 `CHUNK_SIZE = 1024`、`CHUNK_OVERLAP = 200`。
3. 每个分段生成唯一 `chkId`，一份写入关系库的分段表，另一份以文本、ID 和 metadata 的形式提交给向量库。
4. Chroma 使用知识库对应的 embedding function 计算向量，并将结果持久化到 `resources/vector_store/<reposId>` 下的集合中。
5. 摘要、Q&A、三元组等增强内容也会以各自的稳定 ID 和来源 metadata 写入同一个知识库集合，因此它们能够参与统一的语义检索。

这里“写入向量库”并不是把一个向量手工拼接进文件，而是由 embedding function 完成文本向量化，再由 Chroma 负责持久化和检索索引维护。

### 4. WenKB 的问答检索流程

1. 用户输入问题后，向量库使用同一个 embedding 模型把问题转换为查询向量。
2. `similarity_search_with_score` 在当前知识库集合中返回候选文档和分数，候选数量由 `topK` 控制。
3. 当前实现按 Chroma 返回的距离分数进行筛选，代码约定分数越小越相似，并保留小于 `smlrTrval` 的结果。
4. 结果再截取到 `maxCtx` 条，拼接为提示词上下文交给 LLM。
5. 每条命中的 metadata 会转换为来源信息，保存数据集、文件、分段或摘要/Q&A/三元组对象标识，最终形成聊天引用。

因此，完整链路可以概括为：

```text
原始资料 -> 文本切分 -> embedding -> 向量索引
用户问题 -> embedding -> 相似度检索 -> 上下文 -> LLM -> 答案与引用
```

### 5. 为什么必须保持 embedding 模型一致

向量的“坐标系”由 embedding 模型决定。即使两个模型都输出相同长度的向量，它们各维度所表达的语义也不一定相同；如果使用模型 A 建库，再用模型 B 查询，距离值就缺乏可靠的可比性。切换模型后，应重新对所有分段和增强对象编码并重建索引。

这也是 WenKB 设计中要求知识库绑定 embedding 模型、已有索引后谨慎切换模型的原因。LLM 可以更换而不必重建向量索引，但 embedding 模型变化通常会影响索引兼容性和检索质量。

#### 在 WenKB 中的对应关系

- **设计目标**：概要设计将索引构建拆为文本切分、向量化、索引持久化和失败状态回写；问答模块复用向量检索并返回来源。
- **向量存储**：`repos_vector_db.py` 以 `reposId` 作为 Chroma collection 名称，使用 `PersistentClient` 将集合保存到知识库对应目录，并提供新增、查询、更新、删除和删除集合能力。
- **embedding 选择**：`llm_client_tools.py` 的 `get_repos_embedding_function` 读取知识库绑定模型和创建人配置；当前支持本地 HuggingFace embedding、Ollama embedding 和 OpenAI 兼容 embedding。默认本地模型通过 `HuggingFaceEmbeddings` 加载，并启用向量归一化。
- **主索引构建**：`dataset_to_vector.py` 负责解析、切分、生成 `chkId`、保存关系库分段并批量写入向量集合。
- **问答检索**：`ask_to_llm.py` 调用 `similarity_search_with_score`，按 `topK`、`smlrTrval` 和 `maxCtx` 组织上下文，再将 metadata 转换为聊天引用。
- **数据边界**：关系库保存分段、摘要、Q&A、三元组、任务状态和错误信息；向量库保存语义检索副本；原始文件仍保存在文件系统中。

#### 需要注意

- **设计与实现差异**：数据库设计建议的 `similarity_threshold` 默认值为 `0.30`，而当前代码配置 `SIMILARITY_TRVAL` 为 `1`；同时当前实现明确按“距离越小越相似”筛选。后续若调整默认值或切换距离语义，应同步更新前端提示、配置文档和测试。
- **索引不是原始数据的唯一来源**：删除、修改分段或删除知识库时，关系库和向量集合都要同步处理；出现单边失败时需要依靠错误记录和重试机制恢复。
- **模型资源必须完整**：本地 embedding 模型目录、权重文件和运行依赖不完整时，向量集合可能无法加载。当前维护记录已经针对 `m3e-small` 的 Torch、fsspec 和 Git LFS 占位权重问题增加校验。
- **检索质量不只取决于模型**：分段长度、重叠大小、`topK`、相似度阈值、metadata 过滤和原始内容质量都会影响最终结果。
- **可改进方案**：可在集合或知识库元数据中保存模型 ID、版本、向量维度、归一化方式和索引构建时间；模型变更时自动标记旧索引失效并触发重建，减少“关系库配置已更新但向量仍是旧模型”的隐性错误。
